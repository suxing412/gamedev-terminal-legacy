# 技术方案 · 坐席间沟通页与主页群聊的分工

日期：2026-08-29
作者：总监（据制作人 01:57 设想）
状态：待异厂对抗评审
范围：`gamedev-terminal` 的 `/chat` 页与主页坐席台

---

## 零、制作人的设想（原话要点）

- `/chat` 做成**坐席之间**的沟通页，形制类似 Discord / 微信
- 两个坐席要沟通就拉一个窗口；窗口**常驻不删**，下次这两席还沟通仍用这个窗
- 本地与 GitHub 远端**双留痕**，出问题能迅速遍历找到沟通位置
- 分两型：**短期窗口**（遇到问题拉起讨论，讨论完结纪要，窗口消失）与**长期常驻**

---

## 一、第一性原理：一个「沟通窗口」到底在承载什么

不看 Discord 也不看微信，从头问：一条会话通道成立，靠的是什么把它和别的通道分开？

只有三样可能的分法：**按参与者 / 按话题 / 按时段**。

| 分法 | 找东西时怎么问 | 什么时候是对的 |
|---|---|---|
| 按参与者 | 「我跟老王说过什么」 | 关系长期存在，话题不可预测——**人类 IM 的默认** |
| 按话题 | 「TK-185 那事当时怎么定的」 | 话题有始有终，参与者随话题聚散 |
| 按时段 | 「上周三发生了什么」 | 只在回溯时有用，不适合当主索引 |

### 1.1 一个必须先说破的矛盾

**制作人给的目的是「出问题能迅速遍历找到沟通位置」——那是按话题找。
而给的结构是「项管↔总监一个常驻窗」——那是按参与者存。**

存的轴和找的轴不是同一根。后果可预期：三个月后那个「项管↔总监」窗里躺着几百条互不相干的事，
要找「TK-185 当时怎么定的」得在里面翻——**正是这个设计本来要消灭的那件事**。

人类 IM 用参与者做主轴，是因为**人有连续的记忆**：你记得「这事是跟老王聊的」，
于是参与者是有效的检索线索。**而坐席没有这种记忆**——它们是带上下文的模型调用，
「项管和总监的关系」除了日志里那些字之外不存在于任何地方。
把人类 IM 的索引轴原样搬过来，是把一个建立在人类记忆之上的便利，搬到一个没有记忆的主体上。

### 1.2 所以主轴该是话题，参与者是过滤器

**主轴：话题（一个窗口 = 一件事）。参与者：这件事上谁在场，随话题定。**

这样两种检索都成立：
- 「TK-185 那事」→ 直接命中那个窗
- 「项管跟总监都聊过什么」→ 按参与者过滤，列出他们共同在场的所有窗

反过来（参与者做主轴）则只有第二种成立，而第二种恰恰不是制作人说的那个需求。

### 1.3 那「长期常驻 vs 短期」的区分还成立吗

成立，但它不是两种**窗口**，是**同一种窗口的两种寿命**：

- **有始有终的**：一件事讨论完 → 结纪要 → **归档**（从活动列表移走，但永远查得到）
- **长流水的**：某些话题天然不结束（如「排期咬合」「额度水位」），一直开着

判别标准不是「谁跟谁」，是**这件事会不会完**。

### 1.4 「窗口消失」这条要改

制作人原话是短期窗口讨论完「窗口就消失了」。**消失不能是真消失。**

这个页面的立身之本是「出问题能查到当时怎么说的」。若窗口真删，
留下的只有纪要——而纪要是二手的、是当时那个坐席的总结，
**恰恰在出问题的时候最不可信**（出问题往往就是因为当时的总结漏了什么）。

改成：**归档 = 从活动列表移走 + 纪要置顶 + 原文全留**。
界面上不出现在默认视野里，检索时照样命中。

## 二、这一页与主页群聊，各自回答什么

两页不重的唯一理由，是它们**回答的问题不同**，而不是「一个是群一个是私」。

| | 主页群聊 | 坐席间沟通页 |
|---|---|---|
| 谁在场 | **制作人在场** | 坐席之间，制作人不必在 |
| 回答什么 | 「现在什么等着我 / 我问一句谁答」 | 「这事当时是怎么议的」 |
| 读法 | **扫**（抬眼余光，最近几十条） | **查**（按话题/参与者/日期检索全量） |
| 流量级别 | 人类说话的量：一天十几句 | 机器协作的量：实测项管一人产 311 条 |
| 不看会怎样 | 漏掉该拍板的事 | 不会怎样——它本来就不要求你看 |

**分家的硬理由是流量级别差一个数量级。**
实测：`遥控/thread.jsonl` 共 325 条，项管 311 条（96%）、制作人 12 条、Claude 2 条。
把协作流量放进制作人看的屋子，就是把 PRODUCT.md 开篇那个病
（「该他拍板的事被技术汇报淹没」，一张单在队列里停了 160 小时）原样重造一遍。

## 三、一条必须写死的约束：讨论不产生决定

坐席之间可以商量、可以彼此质疑、可以给建议。**但凡碰到人闸（放行/验收/废弃/定夺/方向），
不许在这一页里达成结论然后执行。**

没有这条，这一页会变成「决定在制作人看不见的地方做掉了」的温床——
而这套协议的全部立意就是人闸在制作人手里。

**落法**：坐席发言里出现人闸类动作词时，该窗自动打「候人闸」标，
并把这一条推到主页的「等你拍板」栏。**这一页只留讨论，结论必须浮上去。**

---

## 四、一条更根本的质疑：坐席之间真需要「聊天」吗

这条是对制作人设想的正面质疑，不是补充。

今天一个坐席 = 一次带上下文的模型调用。「项管跟总监聊」的物理含义是：
生成项管的话 → 喂给总监 → 生成回复 → 再喂回去。**每一轮都是真金白银，且没有天然的终止条件。**

所以要问：坐席之间对话解决了什么，「一个上下文更全的 agent」解决不了？

诚实的答案：**价值不在对话本身，在两件副产品**——
① **关注点分离**（财务只揣额度数据、项管只揣排期，谁都不用扛全部上下文）
② **可审计的交接记录**（为什么这么定，事后查得到）

而这两件都由**结构化交接**给出，不需要自由聊天：
「财务 → 项管：这批超支 1.8 倍，建议压」是有价值的一条；
财务和项管来回二十轮把这件事聊透，是烧钱。

**所以设计取向定为：窗口是留痕与检索的容器，不是让模型自由发挥的场子。**
每次交换都要有由头、有终止。具体两条闸：
- **轮数上限**（默认 6 轮，超了自动结纪要并归档，标「未收敛」）
- **无人点名不自动接话**（坐席不因为「群里有人说话」就应答；只应答 @ 到自己的）

---

## 五、GitHub 远端留痕：要，但不是每条都推

制作人要远端留痕。理由成立（异地耐久、跨机可读、git history 本身可审）。
但**每条消息一次提交**会把仓库变成噪声场，且推送失败会阻塞对话。

**改为：本地即时落盘，远端按批归档。**
- 本地 `坐席沟通/<话题ID>.jsonl` 即时追加——对话的真相在本地，不依赖网络
- 归档时（结纪要 / 轮数到顶 / 每日定点）成批提交一次
- 推送失败**不阻塞对话**，只在界面标「远端落后 N 条」

## 六、落地设计

### 6.1 目录与数据

```
<部署区>/坐席沟通/
  索引.jsonl                ← 一行一个话题：ID/题/参与席/起于/状态/纪要/远端已推至
  话题/<ID>.jsonl           ← 该话题的全部发言，只增不改
```

**话题 ID 不用自增数**：用 `<日期>-<短随机>`，因为并发开窗时自增会撞。

### 6.2 状态机（三态，不多）

`活动` → `已归档`（结了纪要） / `未收敛`（轮数到顶还没结论）

**没有「删除」态。** 见 1.4。

### 6.3 页面

- **左栏**：话题列表。默认只显示 `活动`；顶上一个筛（参与席 / 日期 / 关键词 / 含归档）
- **右栏**：选中话题的全部发言 + 纪要（若已结）置顶
- **顶部**：`+ 新话题`——选参与席、写题、写由头

### 6.4 与主页的接线

- 坐席发言命中人闸词表 → 该话题打「候人闸」标 → 推一条到主页「等你拍板」
- 主页那一条点进来直达该话题

---

## 七、明确不做

- 不做「未读红点」——这一页本来就不要求制作人跟读，红点会把它变成又一个催人看的东西
- 不做实时推送（SSE/WebSocket）：查的读法不需要秒级
- 不做坐席主动发起话题（本期）：先由制作人或总监开窗，避免自发聊天烧额度
- 不做跨话题的 @ 引用

## 八、验收标准（逐条机器可判 · H104）

1. **话题主轴**：造三个话题（同两席、不同事），断言检索「话题关键词」各自只命中一个，而非命中一个混合窗。
2. **参与者过滤**：同上三话题，按「项管」过滤，断言三个都出现（参与者是过滤器不是主轴）。
3. **归档不删**：归档一个话题后，断言默认列表不含它、含归档的检索能命中它、原文逐字仍在。
4. **纪要不替代原文**：归档后断言 `话题/<ID>.jsonl` 行数与归档前相同。
5. **轮数闸**：喂 7 轮对话，断言第 6 轮后自动归档并标「未收敛」，第 7 轮不再调用模型。
6. **无点名不接话**：一条不含 @ 的坐席发言，断言零模型调用。
7. **人闸浮出**：坐席发言含「废弃/验收/放行/定夺」，断言该话题打标且主页待拍板栏多一条。
8. **本地先于远端**：断开远端后发言，断言本地照常落盘、界面标「远端落后 N 条」、对话不受阻。
9. **并发开窗不撞 ID**：并发开 20 个话题，断言 20 个 ID 互不相同。
10. **读不到就说读不到**：索引文件不存在时，断言页面显示「读不到」而非「零个话题」。

## 九、留给评审的已知薄弱处

1. **话题为主轴与制作人原话（参与者为主轴）不一致**——第 1.1 节给了理由，但这是对制作人设想的改动，需要他点头。
2. **轮数上限 6 是拍脑袋的数**，没有实测依据。
3. **人闸词表**用正则匹配中文动作词，必然有漏有误——漏了就是「决定在暗处做掉」，误了就是噪声。
4. **归档时机**若只靠坐席自己「结纪要」，会出现永远不结的话题；轮数闸是兜底，但兜底触发时纪要质量差。
5. **本期七席只有两席接模型**，坐席间对话在五席未接的情况下基本发生不了——这一页可能建好了没有流量。
