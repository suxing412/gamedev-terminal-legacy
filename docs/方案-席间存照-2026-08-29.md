## 一、本稿最大的一处改动：附件是视图，不是归档

前两稿都栽在同一个地方——**试图把消息「分」成两堆**（对话流 / 附件），
于是每次分错都会把东西藏起来。复评击杀③⑧说得很准：
一条 `验收报告 TK-312` 不含写死的四个标记词，就会被判成对话；
而词表每加一个词，都要回查全部历史、区分「真报告」与「引用了『验收报告』四个字的普通答复」。

**根子上的错是「分堆」这个动作本身。**

### 1.1 改成：一条不动，附件只是一层标记 + 一个筛

- **所有消息都留在对话流里**，一条不移、一条不藏
- 判为产出物的那些**多带一个标记**（一行摘要条），并进「附件索引」
- 「只看有附件」是**筛**，不是**另一个抽屉**

三个后果，逐条对着击杀：

| 原问题 | 改后 |
|---|---|
| 分错就藏起来（击杀③） | **分错只是少一个标记，东西还在流里看得见** |
| 词表演进要回查历史（击杀⑧） | 标记**读时计算、不落盘**，词表改了下次读就是新的，无历史可回查 |
| 分型与折叠矛盾（上轮击杀③） | 两者正交：折叠只看长度，标记只看形态，互不引用 |

**误判的代价从「藏住内容」降到「少一个标记」。** 这是本稿唯一真正的结构性改动。

### 1.2 三型仍然成立，但只有播报是真的「不进本页」

| 形态 | 条数 | 处置 |
|---|---|---|
| 说的话 | 198 | 在流里 |
| 交的东西 | 12 | **也在流里**，另带附件标记、进附件索引 |
| 状态播报 | 115 | **不进本页**（九成已在瞭望塔流水，且它没有说话对象） |

播报是唯一被排除的一类，因为**它不是「谁对谁说了什么」**——排除它不是分类判断，是范围判断。
且底部明写条数与去处（§2.5），不静默隐藏。

## 二、逐部分的第一性原理

### 2.1 条目 ID：行序 + 内容，不改写口（三评击杀①）

历史 325 条**没有一条带 id**（实测：字段只有 `t`/`from`/`text`）。

二稿拟 `t + from + sha1(text)`，实测当前零碰撞——**但三评指出重试写入会产生
三者全同的两条**，那时 ID 必然相同，分页锚点与前端 key 都会撞。这条在包络内成立
（现在 0 条，但重试随时可能发生），故改：

```
条目ID = 行序 + '|' + t + '|' + sha1(text).slice(0,8)
```

**行序 = 该条在文件中的行号（从 1 起）。** 这条线程只增不改（append-only），
故行序对已有条目永不变化，是天然的不可变序号——不需要写侧配合、不需要迁移历史。

性质：读时可算、不落盘、历史与将来一视同仁、**重试写入的两条也能区分**。

**依赖的不变量**：`thread.jsonl` 只增不改。若哪天引入重写或轮转，行序即失效——
这条依赖写进 §七，改动者要回来看。

### 2.2 坐席名单（左栏）

- **问**：这屋里有哪些角色，谁真的能说话
- 数据源：`/api/seats` ← `server/lib/坐席.js` 的 `接模型` 字段。
  **这是配置事实，不是运行时连接状态**——本期不画在线/离线灯，
  坐席是按需调用的模型，没有常驻连接，画了就是画一个不存在的东西
- 未接模型的压暗并标「未接」

### 2.3 对话流

- **问**：他们之间说了什么
- 一条 = 发言人 + 时刻 + 正文；**>6 行截断 + 展开**（折叠只看长度）
- **分页与游标**（复评击杀⑦、三评击杀②）：默认只出最近 60 条，向上滚加载。
  **游标是行序，不是 offset**——用 offset 的话，边加载边追加会把同一批再取一遍
  （三评构造：首屏取 m141~m200 后追加 m201~m260，`offset=60` 会重新得到 m141~m200）。
  行序是绝对位置，追加不影响已取区间的编号，天然免疫这个问题。
- 不做未读红点：本页不要求跟读

### 2.4 附件标记与索引

- **问**：他交出来的东西是什么
- **判别**：正文首行像标题（≤30 字、无句末标点）**且**命中产出物词
  （报告/清单/回执/纪要/复盘）**或**首行含工单号形态（`[A-Z]{2}-\d+`）。
  比写死四个词宽，且**判错只是少个标记**（见 1.1）
- **展开零额外请求**：正文本来就在流里，附件行只是它的摘要——不另设按 ID 取正文的接口
- **附件索引扫全文件，不扫当前页**（三评击杀⑥）：
  否则唯一那份附件在最早第 1 条、而首屏只有最近 60 条时，点「只看有附件」得到空结果，
  要人工向上翻 83 页才发现它——**把一次查档变成线性翻页**。
  包络内 325 条扫一遍是毫秒级，不构成成本。

### 2.5 播报的去处（三评击杀④）

**判别必须同时看发言人与前缀**，只看前缀是个雷：
制作人发一条「排期复判：TK-312 应回滚，先不要合并」——有明确说话对象、是真对话，
却会被前缀规则排除，**直接违反「一条不藏」**。当前实测这类 0 条，但规则本身是错的。

三稿改成「`from === '项管'` 且命中前缀」。**四评证明这还不够**：
`{from:"项管", text:"排期复判：TK-312 的回执请总监今天签字"}` 同样命中，
**但它是明确指向总监的对话**。

**我在同一处已经加过一次规则，这次证明加规则不解决问题。**
根子是数据缺字段：`t` / `from` / `text` 三样里，**没有任何一样能回答「这是不是说给人听的」**。
没有收件人、没有消息类型，判别在数据层就是不可判的。

### 2.5.1 承认能力边界，改成「折叠」而不是「排除」

既然判不准，就**不许用它做排除**——排除的代价是静默藏掉真对话，而这违反「一条不藏」。

改成：
- 命中播报判别的条目**仍在流里**，但**默认折叠成一行**：`项管 · 排期复判 · 02:14`
- 顶部一个开关：`展开例行播报（N 条）`
- **判错的代价从「藏掉一条对话」降到「一条对话被折了一行」**——点开就在，没有任何东西消失

这与 §1.1「附件是标记不是抽屉」是同一条取向的第二次应用：
**凡是判不准的分类，都不许用来决定「显示或不显示」，只能用来决定「先展开还是先折叠」。**

实测支持这个改法：115 条播报里有 8 条含「确认／准不准」这类对话特征词，
逐条看过仍是播报（词出现在正文中间，不是在跟谁说话）——**说明关键词判别在这件事上本就不可靠**，
当下没出错只是运气。

底部明写：「另有 N 条例行播报未列（排期复判／产线空转／到点无单／零派发），见监视页产线流水」。
N 由一次全文件扫描得出——包络内 325 条一遍是毫秒级，不做缓存（缓存会带来失效一致性问题，
在这个量级上是拿复杂度换不存在的收益）。

### 2.6 半行与并发读（复评击杀②）

写方可能正在追加。读侧规则（与监视器取数层同一口径，那边已有判据顶着）：
- **末行解析失败不算坏行**，跳过等下轮
- **非末行解析失败 = 坏行，计数并在页面显示**，绝不静默跳过
- **末行半行超过 5 分钟仍未补全 → 报「末条记录未写完（已 N 分钟）」**（四评击杀④）。
  原样写「等下轮」在写方崩溃或磁盘满时**永远等下去**，页面既不报坏行也不提示缺失，
  **那一条就永久不可查了**——而这一页的立身之本恰恰是可查。等待要有上限。
- 不加锁、不做快照：这条线程只增不改、单写口（见包络），末行重试足够

### 2.7 筛选与规模红线

- 三个筛：发言人 / 只看有附件 / 关键词
- **红线只看体积，不看条数**（三评击杀⑨）：二稿写「条数 > 5000 **或** 体积 > 20 MB」，
  而实测一年才 6243 条 / 3 MB——**条数那一半会在文件仅 5 MB 时就把筛选关掉，
  正好在人最需要查档的时候切断核心能力**。条数与成本无关，体积才有关。
  改成：**仅当文件 > 20 MB 时**顶部提示「已超出无索引可承载的规模，筛选已停用」。
  按实测增速，这一天在**六年以后**。
- **路由**（三评击杀⑤）：二稿写「`/chat` 保留 302 到新路径」，
  同时又把 `/chat` 定义为本页——**一个响应不能既是本页 200 又是 302**，我自己写矛盾了。
  改成：**路径不变，仍是 `/chat`；只改页签与标题的显示名**。
  没有迁移、没有重定向、没有旧链接失效。名字是给人看的，路径是给机器用的，两者不必同步。

## 三、存照引用：本轮不做，前置三件（复评击杀①②⑨）

制作人 02:2x 提出：主页群聊问一件事，若席间存照有对应记录就直接抛给你。

**这个判断是对的——一个要靠人记得去查的档案基本是死的。**
但我给的实现方案不成立，且三个坑都不是调参数能解决的：

| 坑 | 复评的击杀 |
|---|---|
| 让模型挑 ID 要喂全量语料 | 325 条约十万中文字符，每天 100 问 ≈ **千万级输入 token**；而本方案还写着「零新增模型调用」，自相矛盾 |
| 结论冲突无时序策略 | `m42「TK-146 已修复」`与 `m108「TK-146 回滚待复核」`同时命中，**抛给你的可能正是错的那条** |
| 逐字节比对无规范 | 「解析后的字段值」还是「原始序列化字节」？未定义，验收断言写不出来 |

**前置三件**（各自是一张单的量）：
1. 一个能预筛候选的检索层（代码先筛到十条以内，模型只在候选里挑）
2. 冲突与时序策略（同一话题多条相反结论时，抛最新的？抛全部并标时序？）
3. 引用正文的规范：**取解析后的 `text` 字段值**，不是原始字节——
   换行等转义在 jsonl 里是 `\\n`，显示时必须是真换行，两者不可能逐字节相同

本稿把这一节整体移出范围，**留作后续单**。

## 四、验收标准（逐条机器可判 · H104）

1. **一条不藏**：喂含三型的夹具，断言「说的话」与「交的东西」**全部出现在对话流里**，
   条数等于夹具中非播报条数。
2. **附件是标记不是抽屉**：那条 `验收报告 TK-312`（不含旧词表四词）断言**在流里**；
   若它被判为产出物则另带标记，**判不出也不许消失**。
3. **折叠与标记正交**：一条 3000 字无标记文本，断言在流里、被截到 6 行、无附件标记。
4. **标记读时计算不落盘**：改判别词表后重跑，断言无需迁移、结果直接变。
5. **ID 可算且零碰撞**：对全量夹具算 ID，断言两两不同；同一条重算两次断言相同。
6. **分页**：喂 200 条，断言首屏只渲染 60 条且有「向上加载」。
7. **规模红线只认体积**（四评击杀①：三稿改了正文没改判据，留了一条永远跑不绿的验收）：
   造 5001 条但仅 1 MB 的夹具，断言**筛选照常可用**；造一份 21 MB 的夹具，断言筛选停用并提示。
8. **半行不误报 / 坏行要计数**：末行截断断言不计坏行；中间坏行断言计数并显示。
9. **末行长期不闭合要报**（四评击杀④）：末行半行持续超过 5 分钟仍未补全，
   断言页面出现「末条记录未写完（已 N 分钟）」——**永远等下轮等于永久藏一条**。
10. **播报只折不删**（四评击杀③）：喂一条 `{from:'项管', text:'排期复判：…请总监签字'}`，
    断言它**在流里**（折叠态），断言展开开关能把它展开；**断言页面任何状态下都不会让它消失**。
11. **底部计数与折叠一致**：断言「例行播报 N 条」的 N 等于被折叠的条数。
12. **未接模型的席标出来**，且页面**不含**「在线/离线」字样。
13. **读不到就说读不到**：断言不显示「0 条发言」。
14. **零新增模型调用**：整轮渲染断言模型调用计数为 0。
15. **路径不变**（四评击杀②：三稿改了正文没改判据）：断言 `GET /chat` 返 **200 且是本页**；
    断言全仓不存在指向「新路径」的重定向。
16. **「行」的定义是逻辑行**（四评击杀⑥）：折叠按 `\n` 切分的逻辑行数算，**不按视觉换行**——
    视觉行依赖字体/视口/浏览器，机器判不了。判据：喂一条 3000 字**无换行**的正文，
    断言它**不被折叠**（逻辑上只有 1 行），且页面靠 CSS `max-height` 控制视觉高度。
    这两件事分开：折叠判据看逻辑行，视觉高度归样式。

存照引用不可行、缺运行包络、改正文没改判据），值那个钱；四五两轮里好几条打的是
我上一轮刚加的补丁，且场景越来越极端。

**击杀制要求评审必须构造出失败场景——一个足够坚决的对手，对任何非形式化证明的设计
都构造得出来。** 继续下去是用最贵最慢的方式去找那些「写代码十分钟就会撞出来」的问题。

以下三条便宜且真，收进方案；其余交给判据在实装时撞。

### 6-2-1 类型契约：正文可能不是字符串（五评击杀④）

一条**合法 JSON 但 `text: null`** 的记录不会命中「解析失败的坏行」，
却会让 `sha1(text)`、首行判别、逻辑行统计全部抛错——**整页 500**。
实测当前 0 条，但一条就够。

**契约**：读到的每条先过一次形状校验——`t` 是可解析时刻、`from` 是非空字符串、
`text` 是字符串。任一不满足 → **计入「结构坏行」并在页面显示**（与解析坏行分开计数，
因为成因不同：一个是写坏了，一个是写了个合法但不该有的形状）。

### 6-2-2 折叠计数的验收自相矛盾（五评击杀②）

我写的判据「N 等于被折叠的条数」——展开之后折叠数变 0 而 N 仍是 1，**没有实现能同时满足**。
是我把「有多少条播报」和「此刻折起来几条」当成了同一个数。

**改**：N = **命中播报判别的条数**（与展开状态无关）；
文案改为「例行播报 N 条 · 已展开／已折叠」。判据只断言 N 与判别结果一致。

### 6-2-3 向上加载要单飞（五评击杀⑤）

滚动观察器在首个请求返回前触发两次，两个 `beforeLine=266` 都会取回同一批。
行序游标解决的是「追加不影响已取区间」，解决不了「同一请求发两次」。

**改**：加载走单飞——进行中不再发第二个；返回后按行序幂等合并（已有的行不重复插）。
与监视页清账钮同一形制（那边已有判据）。

## 七、包络外的已知失效场景（不在本轮管，但写明什么信号出现时必须回来）

三评构造的这四条**都是合法击杀**，只是它们的前提在 §零之前的包络之外。
**记下来不是为了驳回，是为了将来包络变了有人知道该回来看哪几条。**

| 场景 | 假设 | 实况 | **什么信号出现时必须回来重做** |
|---|---|---|---|
| 两个写方交错写同一行，读者看到「中间坏行」 | 并发写 | 单写口（监制台 `relay.append`，HTTP 串行） | **出现第二个写入方**（如坐席直接写盘、或多进程监制台） |
| 60 条各 12 MB → 首屏传 720 MB | 单条 12 MB | 最长 3013 字，差四个数量级 | **单条正文超过 100 KB** |
| 100 人每分钟打开 → 119 GB/小时 | 百人并发 | 单人单机 | **出现第二个读者**（多人或远程访问） |
| 行序失效 | 文件被重写或轮转 | 只增不改 | **引入轮转、压缩或就地重写** |

这四条各自都是「一旦成立就必须重做设计」，不是「以后优化」。
**判别信号写在这里，是为了让它成为可发现的，而不是等出事再想起来。**
