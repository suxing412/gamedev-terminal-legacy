## 零、这份方案要解决的痛

制作人原话：「我不行了，感觉一切东西都会报错」。

这句不是情绪，是一个可诊断的症状：**监视这件事今天分散在四个互不知道对方存在的地方**，
每个地方各自会坏，坏了各自没人喊，而制作人要同时记住四处的健康状况。

今夜的实证：cron 四条从注册起就没响过（坑档案 2026-08-29 条），
而**瞭望塔的时钟信源里写着同样的三个定点**——两套机制做同一件事，一套死了，
另一套活着但没人看得见它做了什么。

---

## 一、第一性原理：监视最少需要几个部件

不看现有实现，从头问：一个「监视」要成立，不可省的部件是什么？

| # | 部件 | 不可省的理由 | 省掉会怎样 |
|---|---|---|---|
| 1 | **采集** | 没有观察就没有事件 | 什么都不知道 |
| 2 | **分拣** | 全量事件对人是噪声；要分出「该看的」 | 淹没，等于没看（inbox 377 条未读案） |
| 3 | **呈现** | 事件必须到达一个能动手的人 | **今天正卡在这里** |
| 4 | **自监** | 观察者自己会死，且死时最不可能有人喊 | 静默失守（G20/G25 立闸的成因） |

第 4 条是本项目反复付学费的一条：**看守者本身也要被看守，否则整条链是单点。**

从这四条推出两个硬约束：

- **约束甲 · 采集与呈现必须解耦。** 采集要与任何会话的生死无关（会话会关、会崩、会被压缩）；
  呈现可以随会话来去。今天会话侧 Monitor 违反了这条——会话一关，那三路观察就没了。
- **约束乙 · 自监信号必须与被监对象走不同的路。** 用同一条路检查自己，路断时检查也断。
  今夜 cron 备份拍与主拍同源，正是踩了这条。

## 二、盘点：今天有四处在监视，互不知情

| 处 | 在哪 | 盯什么 | 生死绑在谁身上 | 呈现在哪 |
|---|---|---|---|---|
| ① 瞭望塔 | `packages/watchtower`，独立进程 | 流水 / 信箱 / **时钟** / 心跳 / 远端 五路 | 自己（有 `--install` 登录自启） | **只落文件，无界面** |
| ② 会话侧 Monitor ×3 | 本会话 | 流水关键事件 / 信箱急件 / 值守心跳 | 会话 | 会话窗口 |
| ③ cron ×4 | 本会话 | 三个报时定点 | 会话 | **从未触发** |
| ④ 监制台闸 G13~G20/G25 | `apps/studio/lib/gatereg.js` | 上面三处的健康 | 监制台进程 | 监制台看板 |

**重复**：①的时钟 与 ③ 完全重叠；①的流水/信箱 与 ② 完全重叠。
**缺口**：①采集得最全、活得最久，却**唯独没有呈现**。

## 三、结论先行：不新造，装窗户 + 退役重复

**不做**：另写一套监视系统。瞭望塔的采集与分拣已经够用且经过实战，重写是拿新 bug 换旧 bug。

**做三件**：

1. **给瞭望塔装窗户** —— 终端新增监视器页，读瞭望塔的三个输出文件，可视化呈现。
2. **退役重复的两处** —— 会话侧 Monitor ×3 与 cron ×4 全部撤掉，采集只留瞭望塔一处。
3. **把监视器配置收进一个文件夹**，JSON 化，可制度化扩展。

## 四、落地设计

### 4.1 目录：`gamedev-terminal/监视器/`

```
监视器/
  监视器.json          ← 主配置：有哪些监视格、各自读什么、怎么判健康
  规则.json            ← 分拣规则（瞭望塔那份的单一事实源，终端只读不写）
  README.md            ← 怎么加一个新监视格（制度化扩展的入口文档）
```

**为什么单独一个文件夹而不是塞进 config/**：监视是一个会长期增长的子系统
（今天 5 路信源，明天可能有引擎、CI、外厂信道）。给它自己的地址，
加一格时人知道该往哪儿看——这正是本仓提案里「等人的事必须有住址」的同一条道理，
只不过这次住址是给配置的。

### 4.2 `监视器.json` 结构（草案，评审后定）

```json
{
  "版本": 1,
  "瞭望塔根": "<部署区>/瞭望塔",
  "刷新毫秒": 3000,
  "格": [
    {
      "键": "流水",
      "名": "产线流水",
      "源": { "型": "行文件", "路径": "瞭望塔流水.log", "尾行": 200 },
      "健康": { "型": "有新行", "阈值毫秒": 900000, "说": "十五分钟没有任何事件即可疑" },
      "呈现": { "型": "事件流", "分档": true }
    },
    {
      "键": "未读",
      "名": "未读账本",
      "源": { "型": "jsonl", "路径": "未读账本.jsonl", "水位": "账本水位.json" },
      "健康": { "型": "积压上限", "阈值": 50 },
      "呈现": { "型": "计数与清单", "可清账": true }
    },
    {
      "键": "塔心跳",
      "名": "瞭望塔在岗",
      "源": { "型": "时刻文件", "路径": "心跳.txt" },
      "健康": { "型": "新鲜度", "阈值毫秒": 90000, "说": "三个心跳周期没更新即判失守（与 G20 同一把尺）" },
      "呈现": { "型": "灯" }
    },
    {
      "键": "监制台",
      "名": "监制台",
      "源": { "型": "HTTP", "地址": "http://127.0.0.1:4270/api/board", "超时毫秒": 4000 },
      "健康": { "型": "HTTP200" },
      "呈现": { "型": "灯" }
    }
  ]
}
```

**扩展口径（制度化的那一半）**：加一个监视格 = 往 `格[]` 里加一条，不改任何代码。
`源.型` / `健康.型` / `呈现.型` 三个枚举各自是一张小注册表，
新增一种型才需要动代码，而**加一个格不需要**。README 里写明这条，并给两个照抄模板。

### 4.3 终端侧：新增 `/watch` 页

- 服务端 `server/routes/监视.js`：按 `监视器.json` 逐格取数，产一份归一后的状态 JSON
- 前端 `public/监视.js` + 页面：可视化呈现
- **默认不轮询整页刷新**，只轮询状态接口，前端做差量更新——常驻屏上整页闪是打扰

### 4.4 「终端跟着主机走」

瞭望塔已有 `--install` 注册登录自启计划任务。终端照抄同一形制：
`终端 --install` 注册一条登录自启任务，指向部署区的 exe。

**开机即有，关机才没有。** 两者各自独立自启——终端挂了瞭望塔照收，
瞭望塔挂了终端照样显示「塔失守」（因为它读的是心跳文件的新鲜度，读不到就是失守）。

### 4.5 自监：谁看着看守者

三层，各走不同的路（约束乙）：

| 层 | 谁在看 | 走什么路 | 它死了谁知道 |
|---|---|---|---|
| 瞭望塔 | 终端的「塔心跳」格 | 读文件新鲜度 | 终端会显示灯灭 |
| 终端 | 瞭望塔的心跳信源 | HTTP 探终端端口 | 瞭望塔记事件 + 弹通知 |
| 两者都死 | 监制台 G20/G25 | 读心跳文件 | 监制台看板立债 |

**三者互为对方的观察者，且没有两条走同一条路。**

## 五、明确不做

- 不重写瞭望塔的采集与分拣
- 不动 `规则.json` 的既有格式（终端只读它，不改它）
- 不做告警的「已读/未读」双向同步（终端清账走瞭望塔既有的 `--ack`，不另立写口）
- 不引入任何第三方依赖（沿用单文件零依赖口径）
- 不做移动端/远程访问

## 六、验收标准（逐条机器可判 · H104）

1. **配置驱动**：往 `监视器.json` 的 `格[]` 加一条已有型的格，**不改任何 .js 文件**，`/watch` 页多出一格。判据：测试造两份配置（4 格 / 5 格），断言渲染出的格数分别为 4 与 5。
2. **健康判定四型各自可红**：新鲜度 / HTTP200 / 有新行 / 积压上限，每型造正反两例，断言健康与不健康各判对一次。
3. **塔死终端显示失守**：造一份 `心跳.txt` 时刻为 10 分钟前，断言该格判「失守」而非「在岗」。
4. **读不到就说读不到**：源文件不存在时，断言该格状态为「读不到」，**且不是 0 或空**（PRODUCT.md 原则 5）。
5. **不写瞭望塔的地盘**：跑完整轮取数后，断言 `瞭望塔/` 下所有文件 mtime 未变。
6. **配置坏了不崩**：喂一份语法错的 JSON 与一份缺 `格` 键的 JSON，断言服务不崩且页面显示「配置读不出」。
7. **自启已注册**：`--install` 后查计划任务存在且指向部署区 exe；`--uninstall` 后不存在。
8. **退役无残留**：会话侧三个 Monitor 与四条 cron 撤销后，断言值守清单文档与 `watchpulse.应有项数` 同步改过（两处不许各写一个数）。

## 七、留给评审的已知薄弱处

1. **轮询而非推送**：终端每 3 秒读一次文件。事件到达与显示之间最坏差 3 秒。
   对值班屏可接受，但如果将来要秒级，得换 SSE/watch。**这是知情的取舍，不是疏忽。**
2. **瞭望塔与终端的部署区必须一致**：两者都按各自的规则解析「部署区根」，
   若解析口径不同就会各看各的目录。今天终端已经踩过一次（PORTABLE_EXECUTABLE_DIR 案）。
3. **清账的并发**：终端若提供清账钮，与瞭望塔守护自身的水位写入可能撞。
   现设计是终端调瞭望塔的 `--ack`（单一写口），但那是起子进程，频繁点会起多个。
4. **`监视器.json` 与 `规则.json` 的关系**：前者管「显示什么」，后者管「什么算事件」。
   两份配置分家是对的，但人容易在错误的那份里找东西。README 要写清。

## 八、评审后修订（2026-08-29 · codex 八条击杀全部采纳）

异厂对抗评审：codex 在席领「可行性红队 + 成本红队」，交 8 条**全部带击杀**；
deepseek 缺席（应答 content 为空），**不变量红队那一卷落空**——评审台明写「采信时须自行补位」，本节末尾自行补位。

### 8-1 三层自监被共享文件路径击穿（原第五节写错了一句话）

**原文错处**：第 4.5 节写「三者互为对方的观察者，且没有两条走同一条路」。**这是错的。**
终端与监制台**读的是同一个 `瞭望塔/心跳.txt`**。盘被拔掉、或该目录 ACL 改为拒绝读，
两层同时失明；且都无法区分**塔死 / 盘死 / 权限死**这三件后果完全不同的事。

**改法**：
- 终端对瞭望塔**两路取证**：① 心跳文件新鲜度（原有）② `watchtower.pid` 里的 pid 是否仍是活进程。
  两路结论不一致本身就是信息：文件旧而进程活 = 塔卡住了；文件读不到而进程活 = 盘/权限出事。
- 界面上「塔失守」拆成三态：**在岗 / 卡住 / 读不到**。读不到时明写读不到哪一路。
- 记入不变量：**任何一层自监不得只有一路证据。**

### 8-2 输出契约未定义（编码 / 原子写 / 轮转 / 半行）

**不是假想**：本仓已栽过——`事件.jsonl` 第 2728 行 133 个前导 NUL，JSON 本体完好却被读侧
`.filter(Boolean)` 静默跳过，账少算一笔而无人知（G17 立闸成因）。

**改法**——终端侧读取契约写死三条：
1. 编码一律按 UTF-8 无 BOM 解；遇 BOM 剥掉不报错。
2. JSONL **最后一行可能是半行**（写方正在追加）——最后一行解析失败不算坏行，跳过等下轮。
3. 非最后一行解析失败 = **坏行，计数并在界面显示**。绝不静默跳过——静默跳过正是 G17 那笔账的死法。

### 8-3 自启任务指向旧路径（与今早假换装同族）

部署目录换了，计划任务仍指向旧 exe：任务「存在」，启动的是旧版本或直接找不到文件。
而原验收只查「任务存在」——**又一次用一个新旧都满足的判据去验证**。

**改法**：
- `--install` 遇同名任务**先删后建**，不做增量修补。
- 验收改为**行为判据**：install → 触发任务 → 探终端 `/health` 读到的 `版本` 必须等于本次部署的版本。
  「任务存在」降级为前置条件，不再是判据本身。
- 任务显式指定工作目录与运行账户；失败时把 Windows 任务的 LastTaskResult 取出来显示，不猜。

### 8-4 HTTP200 会把冒名服务判成健康

4270 被另一个进程占用并返 200 时，`HTTP200` 判它健康。

**改法**：`健康.型` 的 `HTTP200` 改为 **`HTTP身份`**——除状态码外还须断言响应体里有约定字段。
监制台探 `/api/version` 断言有 `码印`；终端自探 `/health` 断言有 `版本`。**通不等于是它。**

### 8-5 未读账本无上限而每 3 秒全扫

账本只增不删，每次刷新全文件扫描，成本随账本寿命线性恶化。

**改法**：
- `jsonl` 型改为**按 offset 增量读**，offset 存在终端自己的状态文件里（不写瞭望塔的地盘）。
- 文件变小（被轮转/重建）时 offset 大于文件大小 → **重置 offset 从头读**，并记一行「源已重建」。
- 单次读取行数封顶（默认 2000），超出只报计数不载全文。

### 8-6 我的第 5 条判据根本跑不绿

原判据「跑完整轮取数后瞭望塔下所有文件 mtime 未变」——**活体塔每 30 秒写一次心跳，必然失败**。
这条判据在写下来的那一刻就是不可能通过的。

**改法**：判据改为对**冻结夹具目录**取数（测试自造一份 `瞭望塔/` 样本，无守护在写），
断言取数前后夹具内所有文件 mtime 与字节数均未变。活体目录不参与该判据。

### 8-7 自启验收漏掉「注册了但启动失败」

与 8-3 同族，合并处置：验收走行为判据（触发 → 读版本），不查存在。
含空格与中文的路径必须在判据的夹具里出现——本机用户名就是中文，这不是边角情形。

### 8-8 清账连点起 N 个子进程

**改法**：清账走**单飞（single-flight）**——服务端一次只允许一个 `--ack` 在跑，
进行中再点直接返「清账进行中」；前端按钮同期禁用并显示进行态。
子进程退出码与 stderr 一并回显，失败要看得见，不做静默重试。

### 自行补位：不变量红队（deepseek 缺席，本席落空）

本设计依赖三条不变量。**依赖而不写下来，就是下一个 8-1。**

**不变量甲 · 瞭望塔的流水与账本只增不改（append-only）。**
终端的 offset 增量读法完全建立在这条上。若某天塔改成轮转或就地重写，offset 会读到错位的字节。
防线：8-5 的「文件变小即重置」是兜底，但**只兜得住变小，兜不住等长重写**。
故此条写进 `监视器/README.md` 的依赖清单，并在瞭望塔侧留一行注释指回来。

**不变量乙 · 终端与瞭望塔解析出的「部署区根」必须是同一个目录。**
两者各有各的寻径逻辑（终端还踩过 `PORTABLE_EXECUTABLE_DIR` 那一坑）。解析不一致 = 各看各的目录，
而界面会显示得很正常。**升格为判据**：终端启动时把自己解析出的根写进 `/health`，
判据断言它与瞭望塔 `watchtower.pid` 里记的 `根` 逐字相同，不同即红。

**不变量丙 · 「读不到」永不折叠成 0 或空。**
已是验收标准第 4 条。此处重申它是**不变量而非功能**：任何新增的格、新增的健康型，
都必须先回答「取不到数时你显示什么」，答不上来不许合并。

### 修订后的验收标准增补（接第六节，编号续）

9. **坏行看得见**：造一份含一行坏 JSON（非末行）的账本，断言界面显示坏行计数 ≥1，且好行照常呈现。
10. **半行不误报**：造一份末行截断的账本，断言不计入坏行、不报错。
11. **冒名不通过**：起一个返 200 但响应体无 `码印` 的假服务占位，断言监制台格判「不健康」而非「在岗」。
12. **塔三态可分**：分别造「心跳新鲜+pid 活」「心跳陈旧+pid 活」「文件读不到+pid 活」三份夹具，断言依次判出 在岗 / 卡住 / 读不到。
13. **offset 重置**：先读一半，再把源文件截短，断言下一轮从头读且记一行「源已重建」。
14. **清账单飞**：并发发起 5 次清账，断言只起 1 个子进程，其余 4 次返「进行中」。
15. **两根一致**：终端 `/health` 报的根与 `watchtower.pid` 的 `根` 逐字相同，不同即红。
