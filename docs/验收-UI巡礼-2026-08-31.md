## 一、这块屏是什么（评审前提）

**单人使用、全屏常驻在 4K 显示器上、整天开着、开机自启。**
不是「打开来用的工具」，是抬眼就在的东西。用户在别处工作（Unity、代码、公司的事），
余光扫这块屏；需要拍板时转过来说几句；夜里睡前看一眼产线还活着没有。

PRODUCT.md 的五条原则（评审请以此为尺）：

1. **状态先于叙述**：「活着 / 在跑什么 / 谁等我」三问必须**不用滚动、不用点击**就能回答
2. **对话是主干道，不是抽屉**
3. **等待中的事有固定住址**，不参与信息流滚动
4. **安静是默认，动是信号**：常驻整天意味着任何动效都是打扰
5. **数字必须是真的**：宁可显示「读不到」，绝不显示占位数

反面参照（明确否掉的）：SaaS 仪表盘卡片网格、聊天机器人 App、霓虹黑客终端、审批工作流软件。
手艺基准：**排版照 Linear，密度与状态色照 Datadog**。

## 二、本轮改了什么（请逐条攻）

### 2.1 右栏事件流：相邻同种折叠

实测 `/api/events` 回 40 条，**去重后只有一种**（`值守心跳 seq=N 应有=7 周期=5m`）。
常驻可见的那一整栏在用 40 行说同一句「还活着」，而「产线刚发生了什么」这一问的答案被刷没了。

改法：`事种()` 把数字归一当作「种」，`折叠()` 合并**相邻**同种为一行（`×N` + 时段）。
只折相邻、不跨过中间插进来的别的事件——「心跳×20 → 一次失败 → 心跳×20」
要看得出那次失败夹在中间。空态与「读不到」分开渲染。

### 2.2 文稿库：按用途分类 + 三条可叠加筛选

**主轴从「哪个仓」改成「这份东西是干什么的」。**
实测语料 951 份：工单留痕 454（48%，机器一次性产出、只读）、项目文档 186、
规章 113、记忆库 71、班报与情报 33、**在办文稿 50（他真正来回改的）**、其它 45。
按仓分组时那 50 份散在三个仓里，跟 48% 的机器产出排在同一条 mtime 倒序流里抢位置。

筛选三条可叠加：**有记号**（记号系统本来的用途）/ 可写 / 类别。
条目改两行式（名 · 日 ｜ 出处 · 记号 · 体积），去掉 `direction:rtl` 的头部截断
——截掉的正是区分它们的那半截。筛完为空有空态与出口。

「有记号」的数据来自开机后扫一遍可写文件（453/951，实测 46ms，之后按 mtime 缓存）。

### 2.3 原始流：把「没出货的源」显出来

源下拉原先只列「数据里出现过的源」，于是**三个颗粒无收的源在这一页完全不存在**
——你看不出「四个源里三个没出货」，只会以为本来就只订了一个源。
改成列全部配置源并标零（零的置灰不可选），另加一行
「今天有 3 个源颗粒无收：… → 去监视页看为什么」。
下拉箭头与复选框自绘（原生的带着操作系统的箭头与系统蓝勾选色）。

### 2.4 四张视图样式表的响应式断点全是死代码

`read.css / watch.css / 班次.css / 存照.css` 的 `@media (max-width: 900px)` 量的是**视口**，
而这些页在主页壳里是被抠成片段塞进中栏那一格的：视口 1280+、容器只有 720
——**断点一次都没触发过**，席间存照因此在 720px 的窄栏里还切着三列。
统一改 `@container 视`，容器声明放 read.css 一处（所有视图页都加载它）。

### 2.5 塔形态下的页签是「点了不动的导航」

视图区长在 `.话栏` 里，而 `.话栏` 在塔态是 `display:none`。
实测：塔态下点「文稿」，片段**真的取回来并塞进了 DOM**，而它宽高都是 0——
点得动、不报错、没反应。改成塔态一并收起页签导航
（这个形态的取向是「余光扫一眼」，要看某页先按形态钮回全屏）。

### 2.6 修掉自己当晚引入的回归

`文稿.css` 写了 `body.页, .视图 { overflow:hidden; height:100% }`。
**每张视图样式表都会被 index.html 预载**，于是这条漏给了全部五页：
席间存照 15487px 的内容被裁在 491px 里，**日报/原始流/监视/班次/存照在壳里全都滚不动**。
当时还专门写了注释「用 body.页 而不是裸 body，免得影响主页三栏」——守住了 body，漏了 `.视图`。
改成 `:has(.稿容)` 限定，并补守卫 `壳.test.js 守①c`。

### 2.7 窄屏兜底

Electron 壳 `minWidth: 1100`，所以全屏态到不了窄宽；但 README 写了「浏览器打开」这条路，
而 420px 下顶栏会散架（七个页签竖着断成单字）。补两级降级（1100 / 820）。

## 四、请重点攻的六个方向

1. **分类是否站得住**：那七个类别是从 951 份语料推出来的。有没有一类文档会被归错、
   或者归对了但用户找它时不会想到去那一类？「在办文稿」组内按 mtime 排，
   50 份要滚几屏？搜索只搜文件名够不够？
2. **筛选是否解决了真问题**：「有记号」今天只有 1 份。当它变成 20 份、200 份时呢？
   三条筛选叠加之后，用户还说得清自己看到的是什么吗？
3. **折叠是否会藏掉该看的**：`事种()` 把所有数字归一。有没有一类事件，
   数字变化本身就是信息（金额、剩余额度、单号），折起来就丢了？
4. **常驻整天的代价**：记号扫描每 8 秒可能重跑一次（列举缓存过期），
   缓存 Map 上限 2000。开机 12 小时后会怎样？
5. **这些改动会不会在 Electron 壳里表现不同**：容器查询、`:has()`、`color-mix()`、
   `appearance:none` 在 Chromium 124 里都可用吗？有没有哪一条在 exe 里静默失效？
   （本项目有先例：细滚条样式在壳里从未生效过。）
6. **还有哪些页没被这一轮照到**：流程树 `docs/流程树-2026-08-31.md` 列了八节 60+ 分支，
   本轮销掉的是其中一部分。剩下的里面哪几条最可能藏着同一类病？
